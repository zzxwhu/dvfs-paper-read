## 先把四个角色放对位置

被控负载是要完成的程序和输入，比如压缩一块日志；CPU是执行程序的硬件；控制器根据观测选运行档位；驱动／寄存器把档位落实。程序代码可以完全一样，CPU时钟变慢时每条指令对应的墙钟时间通常变长，访存或I/O等待则未必按同样比例变化。

软件控制并不意味着没有真实硬件。软件中的学习策略可控制真实CPU；也可先控制一个执行时间与能量模型。后者能验证闭环逻辑，但模型输出的J不能当真实电测。E902的RTL能在仿真中改变时钟并反馈计数；电压导致的物理功耗还需相应模型、功耗分析或板级实验。

## 这篇到底解决哪一件事

先辨认程序处于计算阶段还是访存阶段，再联合调整处理器功率上限和非核心部分频率。

只降低核心功率可能拖慢计算任务，只降低uncore可能伤害访存任务。待验证的假设是：结合阶段识别和两个硬件旋钮，比单旋钮或固定策略更好地平衡能量与性能。

**把方法想成一条流水线：** perf读取IPC/MPO → 离散状态和阶段变化 → 两张Q表评估联合动作 → msr-safe设置RAPL功率帽与uncore频率 → 记录能量及进度 → 更新其中一张Q表 → 下个窗口。

| 先回答的问题 | 本文答案 |
| --- | --- |
| 状态 | IPC=指令/周期；MPO=末级cache miss/指令，经过离散化。 |
| 动作 | 功率帽W和uncore频率GHz的组合；不是压缩等级，也不是神经网络参数。 |
| 奖励 | 最终选择(c·IPC)^3/W，兼顾进度与功率的代理目标。 |
| 周期／平台 | 默认3秒采样；Ubuntu16.04/Linux4.15.0；CascadeLake与Haswell。 |

## 十个先修关键词

| 级别 | 术语／关键词 | 直觉、严格含义与易混点 |
| --- | --- | --- |
| A | DVFS / DFS | DVFS同时涉及动态电压与频率；只有时钟变化称DFS。电压能否改变取决于实际供电域。 |
| A | Workload | 真正执行应用计算的程序与输入；本文里的控制器是另一个角色。 |
| A | Controller | 根据观测选择动作的软件／硬件，可运行在同一CPU或独立控制核。 |
| A | OPP | Operating Performance Point，经过允许范围验证的电压—频率组合。 |
| A | Power / Energy | 功率W表示此刻消耗快慢；能量J是对时间积分。低功率不必然低能量。 |
| B | Deadline | 作业必须完成的时刻；平均时延、P95与最大时延各有不同用途。 |
| A | 功率帽 | 允许处理器平均功率不超过某设置，硬件再调频以满足它。 |
| B | Uncore | CPU核外的共享逻辑，如部分缓存／互连等，组成随平台而变。 |
| B | IPC/MPO | 执行效率与访存压力的计数比值，不是直接功耗传感器。 |
| C | Double Q | 把动作选择与价值估计分开，减少单表最大化偏差。 |

## 它与你的毕设怎么接起来

这篇支持你先试小Q表而不是直接上深网络。单核E902可将动作简化为3–5档频率，状态用近期每字节周期、剩余字节和剩余时间；如果只具备一个可控时钟域，就不要虚构uncore旋钮。功率帽是厂商硬件功能，不能仅靠一张Q表实现。

最先可以尝试：**P0：小Q表替代深网络**。理由是降低部署门槛；最低资源是3–5档频率、离散进度状态、离线轨迹；通过标准是与固定阈值同条件比较净能量及违约。
