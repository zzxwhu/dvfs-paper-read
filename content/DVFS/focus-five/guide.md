## 你关心的五个设计决定

| 问题 | 落到自己的项目上 |
| --- | --- |
| 怎样选择输入 | 先定决策时刻。在处理下一块前，可以知道块长、任务类型、剩余期限和上一块用时。下一块的真实耗时只能作训练标签。做输入消融：仅用块长，再加入历史周期、阶段或队列，按完整输入文件留出测试，检查危险的时间低估是否减少。 |
| 怎样控制 | 起步用频点查表。然后让小回归模型分别预测候选档的时间与能量，先筛掉预计超时的档，再从余下档里选预计能量最低者。没有可行档时记录不可达并走最快安全档。只有任务之间有长期影响时，再用多任务DDQN衡量学习历史的增益。 |
| 输出是什么 | 策略输出一个档位编号及可行标志。PC软件后端把编号映射为驱动支持的请求，E902后端把编号映射为经过验证的PLL配置及必要的电源命令。同步记录请求档、实际档、发出时刻、生效时刻。 |
| 需要真实硬件吗 | 档位选择、约束搜索、状态机顺序可在电脑上验证。真实时延和能量需要真实工作负载、可控时钟及测量手段。只有模型时写明“模型预测J”。实体FPGA上频率变了且电压固定，可以证明板上DFS。验证实际DVFS还要确认目标供电轨可调且在安全范围。 |
| 如何做算法级验证 | 为每种负载、每个候选档准备可对照的时间/能量数据。先离线求满足同一期限的最优档（oracle），再用仅依赖决策前信息的策略在留出任务流上闭环运行。比较最高固定档、简单查表和学习策略的总能量、超时率、尾时延、控制和切换开销。增加预测偏差、队列突发和不可达期限，看策略如何失败。 |

## 一次完整的软件闭环

以CPU图像预处理或分块压缩为候选。worker读一块数据，controller在块开始前读取特征，输出档位编号。执行器按这个编号请求运行worker的那颗CPU的频率。worker完成后返回输出校验值、开始/结束时刻和能量读数。controller用上一块的预测误差更新下一块。若有原生Linux与调频权限，可以用现成驱动作为执行器，并记录实际频率。仅有普通电脑时，用每个输入在不同档的标定表作为执行器模型；调节模型时间轴即可，主机程序的运行时间不代表目标芯片用时。学习模型指负责选档或预测的算法，CV/LLM则是可选的被控应用。

## DVFS是不是独立于CPU之外的系统

**不一定。DVFS是一套分层机制，策略软件可以就在被控CPU上运行，切换控制逻辑和电源/时钟执行部件则可能位于CPU核之外。** “CPU核外”“同一SoC内”“板上独立芯片”是三个不同边界，不要用一个“外部”混在一起。

| 部分 | 职责 | 可选部署位置 |
| --- | --- | --- |
| 选档策略 | 根据负载、期限、温度等决定目标工作档 | 被控CPU上的软件；或另一管理处理器 |
| 驱动/寄存器接口 | 把档位映射为平台支持的请求 | CPU软件与片上寄存器边界 |
| 切换控制器 | 协调升降档顺序、稳定确认、超时与回退 | CPU核外的RTL状态机；或管理处理器固件 |
| 时钟执行部件 | 生成或选择实际CPU时钟 | 芯片/FPGA内PLL、分频器与专用切钟资源 |
| 电压执行部件 | 改变目标供电轨的实际电压 | 集成稳压器或板上独立PMIC，取决于平台 |

你可以采用下面这种候选结构，具体时钟/供电域需要按工程进一步确认。

```text
E902核上运行
  被控任务 → 采集任务状态 → 选档软件
                              │ 写目标档寄存器
同一SoC中的控制模块             ↓
  接收请求 → 切换状态机 → 稳定确认/错误回退
                │                   │
                ├→ 时钟配置/切换 → E902实际时钟
                └→ 电源接口 → 稳压器 → 目标供电轨
```

它意味着E902可以“给自己选档”，不意味着CPU必须亲自用软件指令完成每一步PLL锁定等待。请求发出后，控制模块可以接手转换；切换期间CPU继续执行、切到备用时钟还是暂时停钟，取决于平台实现。CPU降频后其上运行的策略也会变慢，因此控制开销应在实际档位下测量。

另一种结构是在独立管理核上运行策略/固件，使其使用独立时钟或供电域，便于被控核停钟时继续管理。SCMI论文展示的是这类分工，并不说明所有DVFS都必须增加第二颗CPU。Linux CPUFreq也区分选频governor与平台驱动，策略与执行位置应按具体平台理解。[Linux CPUFreq架构说明](https://www.kernel.org/doc/html/latest/admin-guide/pm/cpufreq.html)

前期在PC验证选档策略时可以将执行器替换为模型；接到E902后保留同样的档位接口，再验证时钟、电源与任务的真实响应。独立模块有利于分层测试，但“有一个独立DVFS模块”本身不等于已经测得DVFS节能。

## 与现有PLL、PMIC的接口

工程里的PLL资料对应TSMC 22nm ULP/ULL工艺宏。FPGA原型可保留寄存器语义，用目标器件的PLL/MMCM和专用切钟资源生成合法档。当前top的CLK_PLL来自外部，原测试的500 MHz来自testbench，需要重新综合、做时序收敛和板级验证。PMIC部分已有24位命令和独立I²C代码；真实输出电压由板上稳压器产生。上板前核对板卡型号、供电轨、允许电压范围、可写接口及电压稳定反馈。控制同一供电轨会影响该轨上的其他逻辑。前期可先验证“安全档→请求→等待→确认→失败回退”，再决定是否接实际电源。[AMD时钟动态重配置](https://docs.amd.com/r/en-US/pg065-clk-wiz/Dynamic-Reconfiguration-through-AXI4-Lite) · [AMD供电轨说明](https://docs.amd.com/r/en-US/ug907-vivado-power-analysis-optimization/Power-Supply-Settings) · [Linux CPUFreq](https://www.kernel.org/doc/html/latest/admin-guide/pm/cpufreq.html)

## 可以开始写代码的共同接口

把整个课题拆成四个函数，后期换平台时保持它们的语义稳定。

```python
features = observe_before_decision(job, previous_measurements)
decision = policy(features, legal_operating_points, remaining_deadline)
receipt = actuator.request(decision.point_id)
measurement = worker.run_and_measure_after_applied(receipt)
policy.observe_result(measurement)
```

`observe`只能读取当前可知的信息；`policy`需要返回可行标记；`actuator`区分收到请求和实际生效；`worker`必须做输出正确性检查。真实异步硬件需要考虑请求等待期间的任务执行，这段顺序代码只是最小串行接口示意。

每次决策建议保存：任务/输入ID、释放时刻、剩余期限、原始特征、模型版本、候选P/T、排除原因、选中档、请求和生效时刻、真实档、完成时刻、输出校验、能量来源。这样一次超时可以追到是特征不够、预测低估、选档错误、执行延迟，还是任务本身不可达。

## 怎么判断你的复现已经有意义

先提出一个能被推翻的问题，例如“加入输入块长能否在同一违约率下减少能量”。保留最高固定档、简单查表或利用率规则、学习策略三个对照，并用同一输入序列、相同动作集和测量窗口比较。评价器可用全部标定数据计算事后最优参考，但策略运行时不能得到未来真值。

如果只重算原表，你完成的是结果核算；如果动作能改变软件环境后续状态，你完成的是模型或软件闭环验证；如果真实处理器运行任务且实际频率可观测，你完成了该平台的调频实验；如果供电也真实变化且完成电能测量，才进一步具备实际DVFS能效证据。不同层级都有价值，报告时写清边界。
