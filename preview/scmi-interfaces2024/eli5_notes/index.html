SCMI端到端时延：从零入门#

论文页面 · 本笔记所用 PDF · DOI

整理日期：2026-11-05。读者原创中文解读；原图归论文作者／出版方。未运行作者实验，不是独立复现。

先把四个角色放对位置#

被控负载是要完成的程序和输入，比如压缩一块日志；CPU是执行程序的硬件；控制器根据观测选运行档位；驱动／寄存器把档位落实。程序代码可以完全一样，CPU时钟变慢时每条指令对应的墙钟时间通常变长，访存或I/O等待则未必按同样比例变化。

软件控制并不意味着没有真实硬件。软件中的学习策略可控制真实CPU；也可先控制一个执行时间与能量模型。后者能验证闭环逻辑，但模型输出的J不能当真实电测。E902的RTL能在仿真中改变时钟并反馈计数；电压导致的物理功耗还需相应模型、功耗分析或板级实验。

这篇到底解决哪一件事#

把“写入新频率”拆成Linux发请求、邮箱传输、固件解码、控制任务计算和执行器生效。

控制器即使推理只需几微秒，Linux应答、固件任务排队和下一周期应用可能使总延迟达到毫秒。待验证的是哪一段主导，怎样优化才真正改善应用。

把方法想成一条流水线： CPUFreq请求 → Linux SCMI驱动发送 → 共享内存邮箱与doorbell → ControlPULP ISR → FreeRTOS解码任务 → 功率／温度控制任务 → 写频率 → 完成应答回Linux。

先回答的问题 本文答案
输入 perf_level_set消息、目标性能点、plant温度与功率状态。
输出 经底层约束后的频率与SCMI应答；写请求不等于立即生效。
关键测量 T1发送、T2解码窗口、T3返回；CD为负载变化至实际频率变化。
平台 Linux在A53侧，ControlPULP在FPGA；被控CPU及能量由模型提供。

十个先修关键词#

级别 术语／关键词 直觉、严格含义与易混点
A DVFS / DFS DVFS同时涉及动态电压与频率；只有时钟变化称DFS。电压能否改变取决于实际供电域。
A Workload 真正执行应用计算的程序与输入；本文里的控制器是另一个角色。
A Controller 根据观测选择动作的软件／硬件，可运行在同一CPU或独立控制核。
A OPP Operating Performance Point，经过允许范围验证的电压—频率组合。
A Power / Energy 功率W表示此刻消耗快慢；能量J是对时间积分。低功率不必然低能量。
B Deadline 作业必须完成的时刻；平均时延、P95与最大时延各有不同用途。
A HLC/LLC 高层策略与低层约束／执行控制器。
B SCMI 标准化管理消息接口，传递性能点请求；不是自动优化算法。
B Doorbell邮箱 写共享内存并发中断通知对方处理消息。
C CD 从负载阶段变化到实际频率改变的延迟，包含多层等待。

用一个小算例建立直觉#

Table1均值70.5+603.5+133.8≈807.8µs。若固件实际解码13.15µs，不能把整个603.5µs都归罪于RISC-V解码慢。

全部为秒；T1发送，T2包含平台与Linux等待，T3返回。CD还包括检测、排队、周期与动作应用；T_msg返回完成也不一定是工作负载开始变速的同一时刻。

要防止的误读： 排队、拥塞、周期相位与OS中断尾部可能支配最坏延迟；只报平均无法保证硬期限。

它与你的毕设怎么接起来#

你的软控硬模块应记录四个时间戳：算法决定、命令写入、执行器确认、频率实际生效。先做简单目标OPP/busy/ack寄存器即可，不必为单核毕设完整复刻SCMI。智能算法的预测时间要给执行器留余量，超时回退与升降频顺序由底层保证。

最先可以尝试：P0：四时间戳测延迟。理由是定位真实瓶颈；最低资源是周期计数器、寄存器trace或逻辑分析；通过标准是分别给均值/P95/最大值，不混用算法时间与生效时间。

五分钟自测#

  1. 这篇输出的是下一频率、功率估计，还是通信／控制时序？
  2. 是真实负载硬件实验，还是模型／RTL／HIL？哪些部分是真的？
  3. 最重要百分比的分母和比较对象是什么？
  4. 如果换成单核E902，哪一个输入或硬件旋钮会消失？
  5. 算上采样、推理、切频和空闲时间后，节能是否还成立？
